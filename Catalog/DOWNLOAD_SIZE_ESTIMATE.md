**Дата 2026-10-09.** [Проверяемый учёт всех URL и размеров](DOWNLOAD_SIZE_AUDIT.json) · [Сценарная таблица](STORAGE_ESTIMATE.md) · [Общие правила](../GLOBAL_ASSET_SEARCH_POLICY.md).

## Реальный состав на GitHub

| Группа | Страниц оригинальных ресурсов |
|---|---:|
| Прежние 3D-модели / большие паки / предметные страницы | **435** |
| Новые CC0 2D/2.5D спрайты и изометрия | **42** |
| CC0 материалы и PBR-текстуры | **162** |
| **Итого разных URL** | **639** |

Эти 639 URL — **не количество отдельных моделей**: один ZIP может содержать сотни/тысячи файлов, иногда разные страницы ведут к тем же авторским геометриям. Прямо сейчас библиотека — каталог ссылок, не сохранённый архив ZIP/FBX/PNG.

## Что действительно известно о размере

- У **44 страниц** издатель указал размер конкретного варианта скачивания; в [аудите](DOWNLOAD_SIZE_AUDIT.json) это `size_status=PUBLISHER_STATED`, значение приблизительное из округлённого отображения.
- У **595 страниц** нет опубликованного/проверенного размера в нашей базе — `UNKNOWN`, `size_bytes=null`.
- Для **44 известных опубликованных вариантов** арифметическая сумма округлённых размеров равна **≈3 455,17 МБ, то есть ≈3,46 ГБ**. Это сумма **только выбранной подгруппы**, **не нижняя граница** и не полный вес 639 источников. У файлов с выбором качества/формата размер изменяется.
- **0 файлов скачано и измерено локально**; точная сумма байтов всей библиотеки **неизвестна**.

Примеры: [Pine Tree 01](https://polyhaven.com/a/pine_tree_01) — около 1,31 ГБ в одном представленном варианте; [Fir Tree 01](https://polyhaven.com/a/fir_tree_01) — около 956,57 МБ; [Bark Willow](https://polyhaven.com/a/bark_willow) — 82,15 МБ; [Brick Wall 001](https://polyhaven.com/a/brick_wall_001) — 68,96 МБ. С противоположной стороны [395 изометрических тайлов](https://opengameart.org/content/300-isometric-object-tiles) занимают 4 МБ, а [2000 облаков](https://opengameart.org/content/clouds-6) — 201,8 МБ.

## Рабочий прогноз, если скачать по одной пригодной бесплатной версии каждого из 639 источников

Это **сценарии с вымышленными средними значениями**, пригодные для резервирования дискового места, но не для отчёта об измеренном весе. Здесь 435 старых страниц, 162 текстуры, 42 новые 2D/2.5D-страницы.

| Тип подборки | Допущение среднего веса одного 3D-пака / PBR / 2D файла | Итог |
|---|---|---:|
| Экономная 1K/2K и небольшие паки | 10 / 10 / 2 МБ | **6,05 ГБ** |
| Средняя смешанная коллекция | 50 / 40 / 10 МБ | **28,65 ГБ** |
| Тяжелее: сканы и высокие разрешения | 150 / 100 / 30 МБ | **82,71 ГБ** |
| Максималистская, крупные высокополигональные файлы | 500 / 250 / 100 МБ | **262,2 ГБ** |

В предыдущем, более предметном распределении по площадкам (Kenney/KayKit/Quaternius, OpenGameArt, Poly Haven) получилось **≈33,61 ГБ** для 597 старых источников. Если прибавить новым 42 2D/2.5D по условным 10 МБ, будет **≈34,03 ГБ**. Это лишь **другой сценарий**, а не статистически доказанная средняя.

**Практическая рекомендация для базы на ПК:** сейчас выделять **100 ГБ под скачиваемые ZIP**, желательно **от 200 ГБ под распакованные рабочие копии**. Если собирать все форматы, все разрешения, высокополигональные сканы и все будущие находки — объём может оказаться намного больше.

## Что делать в каждом будущем цикле поиска

1. Сохранить URL **конкретного** источника и выбранный бесплатный формат/версию, которая разрешена для коммерческой игры.
2. Из официального сайта/файлового manifest/Content-Length записать значение `size_bytes`, `resolution`, `format`, `size_source`, `size_verified_on`. Если в UI показывается округлённое «XX MB», помечать `PUBLISHER_STATED` + `size_approximate=true`, НЕ считать измеренным размером.
3. При фактическом скачивании проверить размер архива и SHA-256 локально, собрать список файлов, исключить дубли и не перезаливать чужие архивы в GitHub.
4. Отдельно считать ZIP-размер, сумму распакованных файлов, дубли внутри паков, дополнения. Если размер неизвестен — `null`, не ноль.
5. Переоценивать суммарный объём при каждом новом цикле, включая **все 2D, 2.5D, 3D, текстуры и материалы**, не прекращая поиск после первых трёх вариантов.

**Итог:** для бюджета места под нашу **текущую** коллекцию можно брать около **30–35 ГБ** как средний плановый сценарий, **100 ГБ** как начальный резерв для загрузок и **200 ГБ+** под рабочую распакованную коллекцию. **Фактический общий размер ещё не измерен.**
